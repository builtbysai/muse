Birth date and birthplace: not established -- no source read this run states them. [C38650]

**Relevance:** (1) Myers helps investigate the question the doorway leaves standing: what happens when a demonstration becomes a program -- whether a hand-shown gesture can be generalized into executable rules, so a piece can be built where the viewer's shown action becomes the system that then runs and varies, instead of the system being fixed in advance. (2) The evidence is specific technique, not biography: Peridot (first paper 1986), programming by demonstration for user interfaces, in which the designer demonstrates actions and the system infers the underlying program; and Garnet/Amulet, where constraints are first-class executable relations -- a demonstration-to-inference-to-generalization loop directly transferable to a generative piece. [C38651]

**Doorway:** The 466th doorway. Takes up the open question from the Leslie Mezei study (#845), quoted verbatim: "the animator in ARTA could draw images and movements but could not compute them -- the command set was fixed, rigid, not an open-ended programming system -- so what happens when the hand can teach the tool, when a demonstration becomes a program and the user extends the system by showing it what to do, instead of choosing from the commands it was given?" Myers answers it, and his answer is narrower and more mechanical than "the computer learns". Peridot does not record a transcript of what the designer did; it generates a parameterized procedure from the demonstration, so the same code works for any parameter values. The hand teaches by doing twice: the first showing is an example with concrete values; the second showing is the difference between the two showings, and the system generalizes only that difference -- a fixed offset, the next list item, the same relation to the previous cycle. And the system never teaches in silence: it guesses, asks the designer whether the guess is correct, shows the result immediately, and lets the designer undo the inference if it is wrong. So the demonstration becomes a program, but the program arrives as a question, not a command -- the hand teaches, the tool proposes, the hand corrects. The open question carried forward is the one the wrong guess leaves standing: the system's first guess is right about 80 percent of the time, which means it is wrong about 20 percent of the time, and the correction is always the user's job -- so what happens when the tool's interpretation of a gesture differs from what the hand meant, when the misreading is not an error to be corrected but something the piece is built to hold open, and who gets to decide what the gesture meant? [C38652]

## M1 -- Show it once: the demonstration becomes a rule

**Subject:** A single hand-drawn gesture -- one drag of one mark across the field -- and the many marks that then live by the rule the system inferred from that gesture.

**Visual principle:** One bold trace (the demonstration, drawn in ink black) against a field of many thin traces (the inferred replays, in a single muted colour). The contrast is between the singular, human, slightly wobbly original and the clean, repeated, varied generalization. Density grows from the rule, not from decoration: the more the rule is exercised, the fuller the field.

**Computational mechanism:** Peridot's own. The designer demonstrates; Peridot infers by about 60 simple condition-action rules (50 inferring graphic constraints, 16 of those added from user testing), tried in order by object type, specificity and commonness, with thresholds built in so the designer does not have to draw exactly. When a guess is made Peridot asks in the prompt window whether it is correct; "yes" applies it, "almost" lets the designer supply a new value for a parameter such as the spacing, "no" tries the next rule. Peridot is right on its first guess about 80 percent of the time and almost always within three guesses. The worked example is the property sheet: the designer names the procedure PropSheet, the parameter Items with example value (Bold Italic StrikeThrough Underline Superscript Subscript Inverted), and one active value for the selection; drawing a gray rectangle for a button drop shadow, then a black rectangle over it, makes Peridot notice the black rectangle seems the same size as the gray one, offset by a constant nine pixels, and ask whether that constraint is correct; the designer types y, and the two rectangles are then kept the same size. Iteration is inferred from two examples, not one: the designer copies the first row and edits the second string to refer to the second element of Items, and Peridot asks whether the rest of the elements should be displayed the same way, as an iteration over all elements. Mouse behaviour is demonstrated with a simulated mouse (the real mouse is busy giving Peridot commands): the designer places the simulated mouse's nose over the check-mark icon with the middle button down, Peridot guesses the check mark depends on the single active value and asks whether pressing should toggle, set or clear, and the designer types t for toggle. The finished procedure can then be called with an entirely different list of strings, even one with a different number of elements. The piece records the viewer's drag as a sampled path plus a speed profile, generalizes it into a parameterized procedure applied to 24 marks with varied parameters (start offset, scale, phase, speed factor), and shows its guess as a visible ghost replay: the viewer accepts it (tap) or rejects it, and the system offers its next-best generalization (same path but mirrored, or same shape but constant speed instead of the demonstrated speed profile). The three generalization types, the 24 marks, and the accept/reject step are this study's formalization; the inference rules, the question-and-answer loop, the two-example iteration, and the toggle are Peridot's.

**Artistic opportunity:** The piece makes visible the exact moment a gesture stops being a gesture and becomes a law. The viewer watches their own wobble become a population's behaviour, and the accept/reject step makes them complicit in the generalization -- the rule is theirs, not the machine's default. Distinctive because the picture is a record of a negotiation, not of a command.

**Takeaway:** Show it once, and the system asks what you meant -- the rule is the answer you gave. [C38654]

## M2 -- The ties that hold: one-way constraints as a living picture

**Subject:** A field of rectangles tied together by visible equations, where pulling one pulls the rest.

**Visual principle:** Tension and propagation. Thin dependency lines connect the rectangles into a graph; when one rectangle is dragged, a ripple of movement travels along the lines, near rectangles moving first and far ones lagging. The composition is a diagram that moves.

**Computational mechanism:** Garnet's and Amulet's own. Constraints are one-way: for any property there can be at most one formula calculating its value, and if the other object changes, the object with the formula is re-evaluated, but not vice versa. The canonical Garnet example keeps an arrow-line attached to a circle and a box: the line's endpoints are formulas reading the circle's right and centre-y and the box's left and centre-y, so moving the circle or box moves the line, and moving the line moves neither. Evaluation is lazy: when a variable changes, all constraints depending on it are marked out of date, and when a value is requested the solver demands the values of everything that constraint depends on, recursing to atomic or up-to-date variables and then working back; Garnet re-evaluates more than 3,500 constraints per second. A novel Garnet feature is the indirect constraint: the object a constraint refers to can be reached through a variable, so a feedback rectangle can be constrained to be the same size as whatever object it is on top of, via a slot holding that object. Peridot's version of the same idea has a stated boundary: its constraints cannot handle two sliders representing different values linked by a conversion, the classical Fahrenheit-to-Celsius case -- "Peridot's constraints cannot be used in this case" -- and Myers says the situation does not arise in the low-level interface elements Peridot is designed to create. The piece fixes 8 rectangles and 10 equations (this study's formalization), re-solves the graph downstream on every drag, and shows failure visibly: a rectangle whose constraint cannot be satisfied (a cycle, or a value driven out of bounds) flashes and holds its last valid value, instead of failing silently. The one-way rule, the lazy evaluation, the indirect constraint, and the Fahrenheit-to-Celsius boundary are Myers's; the rectangle count, the equation set, the deliberate cycle, and the failure flash are this study's.

**Artistic opportunity:** A picture of cause itself. Most generative pieces show motion; this one shows why things move, with the why drawn as lines. The ripple lag gives the dry equations a physical, almost elastic feel, and the failure state gives the piece a small drama: a relation that breaks.

**Takeaway:** Pull one rectangle and the graph thinks out loud -- cause travels along the lines. [C38655]

## M3 -- All of them, at once: the set, not the loop

**Subject:** A field of small marks, acted on as sets: everything red, everything near, everything counted.

**Visual principle:** Grouping by property, not by position. Marks sharing a property (colour, size, speed) move as one body even when scattered; the eye learns to see the set, not the scatter. Density and rhythm come from set membership: when a set is addressed, its members pulse together across the whole field, so the picture's unity is logical, not spatial.

**Computational mechanism:** The Natural Programming studies' own. Asked to solve problems on paper, non-programmers operated on sets of objects rather than iterating through them -- "When PacMan eats all of the dots, he goes to the next level" -- tended to use an event-based style for graphics, and used AND/OR/NOT with inconsistent, non-Boolean meanings. HANDS (John Pane's 2002 PhD, advised by Myers) is built from those findings: an event-based system with a concrete model of computation, queries and aggregate operations, in which all operators accept lists or singletons, so iteration is unnecessary -- the paper's example is "set the nectar of all flowers to 0". Ten-year-olds learned HANDS in a three-hour session and solved programming problems; children using the full-featured version performed significantly better than peers using a version modified to be more like typical programming systems. The piece has no loop construct anywhere: the viewer selects a set by a query (drag a ring around marks, tap one mark to select all sharing its colour, or tap one mark to select all sharing its size), and an action (gather, scatter, recolour) applies to the whole set at once, atomically. Aggregate operations are the only control: all, any, count, and "all but one" drive the picture, and a small counter shows the set size, so the aggregate is visible. The three queries, the three actions, the 60 marks and the five colours are this study's formalization; the set-over-iteration finding, the aggregate operators, and the "nectar of all flowers" example are Myers's and Pane's.

**Artistic opportunity:** A picture whose logic is the way ordinary people actually think -- in sets and wholes, not in for-loops. The simultaneous pulse of a scattered set is visually startling in a way a loop never is: things far apart moving as one body.

**Takeaway:** No loop anywhere -- one gesture, and all of them move at once. [C38656]

## M4 -- The wrong guess: three rival generalizations

**Subject:** Three rival generalizations of a single shown action, laid side by side, one of them chosen.

**Visual principle:** Selection as composition. Three panels, each a ghost of what the rule could be; the chosen panel is bold and full, the two refused panels stay faint but visible, so the picture keeps its counterfactuals in frame. The system's first guess is often the least human, and the contrast between the confident-looking wrong guess and the plainer right one is the point.

**Computational mechanism:** Peridot's own, made spatial. Peridot guesses, asks, and tries other guesses when the designer says no; the guess is encoded as a simple condition-action rule, and where multiple rules might apply the feedback part of the rule asks the user whether it should be applied. Since the first guess is right about 80 percent of the time, it is wrong about 20 percent of the time -- and the wrongness is the subject. The piece has the viewer perform one simple action (move one mark to sit beside another, or colour two marks alike); the system enumerates three candidate generalizations, ranks them by fit, and displays all three as ghost panels; the viewer taps one panel to adopt it, and the adopted rule then runs on the whole field while the other two remain as faint ghosts. If the viewer taps none, the system's top-ranked guess adopts itself after 6 seconds -- and the piece records that as a system choice, visually distinct (adopted panel outlined in dashed, not solid, line). The three candidate rule types (same relation to the nearest neighbour; same relation to all marks sharing a property; same relation repeated as a sequence), the 6-second timeout, and the dashed-outline convention are this study's formalization; the guess-ask-try-next loop and the 80-percent first-guess rate are Peridot's.

**Artistic opportunity:** The comedy and pathos of mis-generalization -- the machine's confident wrongness -- is a genuinely human subject, and the kept ghosts make the picture a record of roads not taken. It is also the most direct picture of the naturalness gap: what a person meant versus what the system inferred.

**Takeaway:** The machine's first guess is a picture too -- and it is often wrong. [C38657]

## M5 -- Why did you turn? the picture that answers for itself

**Subject:** A small flock of marks moving by rules, and the visible reason any one of them turned.

**Visual principle:** Cause drawn as annotation. One mark, when asked about, is ringed and its causal chain is drawn: the rule that fired, the neighbour that triggered it, the threshold value that was crossed -- as a small diagram attached to the mark. The rest of the flock stays in soft motion around it, so the explanation is a spotlight, not a freeze.

**Computational mechanism:** The Whyline's concept (Ko and Myers, CHI 2004), with a grounding caveat stated plainly: the Whyline paper itself was NOT read this run; the concept is known from the citation and the survey summaries read, not from its text, and no specific Whyline interface detail is claimed here. The concept: interrogative debugging, in which programmers ask "why did" and "why didn't" questions directly about program behaviour and see answers in terms of runtime events. Debugging studies in Alice found all programmer questions at failure were one of two types: 32 percent "why did" questions, assuming an unexpected runtime action, and 68 percent "why didn't" questions, assuming the absence of an expected action; half of all errors were due to false assumptions in the hypotheses programmers formed while debugging existing errors. In a study with master's students, debugging time fell from an average of 155 seconds per bug to 20 seconds (a factor of 7.8), and programmers with the Whyline completed 40 percent more tasks in 90 minutes. The piece runs a flock on three fixed, visible rules (separation, alignment, attraction to a slow wanderer -- this study's formalization) and keeps a causal trace: for each mark, the last rule fired and the input values that fired it. Tapping a mark asks "why did you turn?" and the piece answers by highlighting the triggering neighbour and drawing the rule and the crossed threshold. Tapping a mark and then a fixed "why not" control asks the counterfactual: the piece shows the nearest unmet condition -- the threshold that was NOT crossed, drawn as a gap between the mark's actual value and the threshold line. The trace is real (recorded from the running rules), not staged.

**Artistic opportunity:** A picture that explains itself is rare in the gallery, and the explanation is itself a drawing: thresholds as lines, causes as threads. The why-not view -- the gap that did not close -- is a genuinely new visual: a picture of something that almost happened.

**Takeaway:** Ask the picture why, and it answers -- including when the answer is "almost". [C38658]

## M6 -- The mother shape: inheritance you can break

**Subject:** One mother shape and her many children, all inheriting from her until one breaks free.

**Visual principle:** Lineage as composition. The mother shape sits large and central; her children radiate around her, each a variation -- same outline, different size, rotation, or fill -- and thin threads connect each child to the mother, so the picture is a family tree drawn as a picture. When a child breaks free, its thread snaps (visibly cut) and it keeps its own look while the others still follow the mother.

**Computational mechanism:** Garnet's and Amulet's prototype-instance model, with no concept of "class". Any instance can be a prototype for other instances; all data and methods are stored in slots, and a function is just a type of value, so methods and data use the same mechanism. An instance inherits slot values it does not override, so changing a prototype's slot immediately changes all instances that do not override it; removing a slot from an instance makes the prototype's value reappear. Setting a value in a slot that does not exist creates the slot automatically, and slots can be added or removed at run time. Amulet adds structural inheritance: when an instance is made of an object that has parts, instances are also made of each part, so a node prototype made of a bitmap plus a text label yields instances with their own bitmap and label instances; and it allows declaring slots non-inherited, so each instance starts with no value. The piece has one mother shape (a simple five-sided form, this study's choice) and 12 children delegating to her; dragging or recolouring the mother changes all non-overridden children at once; tapping a child breaks its delegation for one property (tap cycles which property is overridden -- size, then colour, then rotation; this study's formalization), so it keeps its own value while its siblings still follow; a long press on a freed child re-joins it (thread re-drawn). The lineage threads are drawn from the delegation pointers, so the diagram is the data structure.

**Artistic opportunity:** Inheritance made visible and touchable: the viewer feels the difference between changing the mother (everything follows) and freeing a child (one thing keeps its own mind). The snapped thread is a small, satisfying visual event, and the family slowly differentiates itself into individuals -- a picture of how sameness becomes variety.

**Takeaway:** Change the mother and the family follows -- until one child keeps its own mind. [C38659]

## M7 -- The small hand commands the wall: amplification across two displays

**Subject:** A small framed panel at the bottom of the picture, and the large field above it that obeys the panel's gestures.

**Visual principle:** Scale contrast as the subject: the tiny panel and the vast field, connected by a single visible thread from fingertip to brush. The field's marks are large, slow, and few; the panel's gestures are small, quick, and precise. The eye travels the thread between the two scales, and the amplification -- a millimetre here, a metre there -- is the visual thrill.

**Computational mechanism:** The Pebbles project's own. Pebbles (PDAs for Entry of Both Bytes and Locations from External Sources, begun 1997) investigates handhelds used synchronously with PCs: computing functions and the user interface are spread across all available devices, forming multimachine user interfaces, in which heterogeneous devices share information synchronously while co-located. SlideShow Commander is the flagship: the laptop displays the presentation while the PDA controls it, showing a thumbnail of the current slide, the notes, the titles of all slides, and a timer; the presenter can walk away, jump to a slide, and scribble annotations with the stylus. Remote Commander gives each meeting participant control of the main PC's cursor in three modes: take turns controlling the PC's single cursor; each person has his or her own cursor floating above all applications, for pointing and scribbling simultaneously; or each person has a separate cursor but only for custom applications. Semantic snarfing solves laser-pointer inaccuracy by using the pointer only to indicate an area of interest, then copying the contents there to the handheld, working on them in detail, and copying the final version back -- "semantic" because the meaning of the screen's contents, not just a screenshot, is copied. The Personal Universal Controller sends the handheld a high-level description of an appliance's control parameters and automatically creates a control panel; in a paper-prototype experiment, users made about one fifth the errors and took about half the time on complex tasks compared with the real manufacturers' interfaces. The piece contains a small panel (phone-sized, framed) that acts as a relative trackpad: dragging inside it moves a large brush on the field above, with a fixed amplification factor of 12x (this study's formalization) and a visible offset marker, a thread from the touch point to the brush, and a readout of the amplification; the panel has one fixed second mode (tap to toggle: absolute mapping, where the brush jumps to the panel position scaled up), so the viewer can feel the difference between relative and absolute mapping. The 12x factor and the two mapping modes are this study's; the coupled displays, the remote cursor, and semantic snarfing are Pebbles'.

**Artistic opportunity:** Amplification is a beautiful, underused visual idea: the smallest human gesture becomes a sweeping mark, and the thread makes the causality visible. The piece is about the distance between hand and picture, which is also what every drawing tool is about. Retire-first candidate of this set: of the seven, this one is closest to a tool demo and most at risk of reading as UI chrome; if the set must shrink, retire it first and fold its amplification into M1 as a variant (a demonstrated gesture replayed at 12x scale).

**Takeaway:** A millimetre here, a metre there -- the small hand commands the wall. [C38660]

## Mechanism note -- what is Myers's and what is not

Peridot's inference rules (about 60, 50 for graphic constraints), the first-guess rate of about 80 percent and within-three-guesses almost always, the question-and-answer loop with "almost" as a reply, the two-example iteration inference with its preconditions (same drawing order per cycle, contiguous creation, list element drawn last), the four mouse-behaviour guesses with about eight single-letter questions, the property-sheet worked example (PropSheet, Items, the nine-pixel offset, toggle), the one-way constraint with Field recursion and constraint reversal, the active-value mechanism with SETActive, the stated limitations (no keyboard, no runtime-created objects, no trees or graphs, no submenu sequencing, Fahrenheit-to-Celsius impossible, implementation no longer runnable by 1990), and the evaluation numbers (ten users, 4-15 minutes against 50-500 minutes by programming) are Peridot's. Garnet's KR prototype-instance slots, lazy one-way constraints with gv and gv-indirect, Opal's redraw timings (25.6 ms against 568 ms), aggregates and aggrelists, the six interactor types, and Lapidary/Jade/C32 are Garnet's. Amulet's C++ port, structural inheritance, non-inherited slots, formula constraints with Get-registered dependencies, multiple solvers including the animation solver, six interactor types (five in the CHI 97 short paper), hierarchical command objects with three undo mechanisms, and scripting by demonstration are Amulet's. The natural-programming findings (sets over iteration, event-based style, non-Boolean AND/OR, "set the nectar of all flowers to 0", HANDS) are Myers's and Pane's. The Whyline's why/why-not concept, the 32/68 split, and the 155-to-20-seconds result are Ko's and Myers's -- but the Whyline paper itself was not read this run, so no Whyline interface detail is claimed. Pebbles' multimachine interfaces, SlideShow Commander, Remote Commander's three modes, semantic snarfing, and the PUC's one-fifth errors and half time are Myers's and his collaborators'. The fusions -- the three generalization types and 24 marks in M1, the 8 rectangles, 10 equations, deliberate cycle and failure flash in M2, the three queries and three actions in M3, the three candidate rule types, 6-second timeout and dashed-outline convention in M4, the three flock rules in M5, the tap-cycles-property rule and the five-sided mother in M6, the 12x factor and two mapping modes in M7 -- are this study's own formalizations, labelled as such where they appear. Peridot infers iteration from TWO examples and constraints from ONE example; the two are never reversed. ARTA is Mezei's, not Myers's; Peridot is not key-frame interpolation; the 1964 multi-console vision is Mezei's proposal, not a Myers system. [C38661]

## The arc: from the window manager, to the demonstration, to the toolkit, to what people expect

Myers's career reads as one long move across four questions, and the move is the through-line. First, "the interface itself" (1980-1984): the Incense thesis visualizes program data, and Sapphire is one of the first commercial window managers -- the interface as an object to be built and sold. Second, "the interface by demonstration" (1986-1990): Peridot lets the designer show the interface instead of programming it, and the inference rules, the question-and-answer loop, and the two-example iteration are the answer to the doorway's question in its narrowest, most mechanical form. Third, "the interface as a toolkit of relations" (1990-1997): Garnet and Amulet turn Peridot's constraints and interactors into reusable parts -- prototype-instance objects, one-way constraints, six interactor types, command objects with undo -- so that other people can build interfaces from relations rather than from event code. Fourth, "what people expect" (1998 onward): natural programming studies how non-programmers actually express solutions and builds HANDS to match; the Whyline asks why a program did what it did in the programmer's own terms; Pebbles spreads the interface across whatever devices are at hand. What changed technically: from a window manager, to inference from examples, to a toolkit of constraints and interactors, to languages and devices shaped by observed behaviour. What did not change: the conviction, stated in the 1993 tech report and repeated in the 2000 tools paper, that user interfaces are inherently difficult to design and implement, that there is no silver bullet, and that the work is therefore to make the difficulty visible and manageable -- by asking, by showing the guess, by letting the user correct it -- rather than pretending it away. This arc paragraph is an interpretation built from legs 1-2, not Myers's own words. [C38662]

## The aesthetic logic

Myers's aesthetic is the interface that can be shown rather than written, and the guess that is announced rather than hidden. Peridot's screen is a workshop, not a canvas: the interface being built in the centre, the parameters and active values with their example values at the top, the commands in a menu at the left, the prompt window at the bottom where the system asks its questions in plain words -- and the generated code off to the right, "mainly for debugging Peridot itself". The sparseness is the mechanism's own shape: one-way relations, declared once and maintained forever, with change flowing in one direction only, so the picture is a set of declared ties rather than a pile of effects. The most Myers-like visual in the whole study is not a widget at all: it is the question in the prompt window -- "is this constraint correct?" -- with the designer's single-letter answer deciding what the system will believe. And the honest boundary is stated on the surface too: some relations cannot be one-way, the Fahrenheit-to-Celsius case is impossible in Peridot, the implementation can no longer be run, and the tools paper admits that constraints for UI programmers were among the approaches that did not catch on, because they are unpredictable and hard to debug. A piece built from Myers should carry that honesty with it: the guess on the surface, the correction in the viewer's hand, the failure visible when a relation cannot hold. This paragraph is an interpretation built from legs 1-2, not Myers's own words. [C38663]

## Rejections

Twelve candidate directions were considered and not queued. A literal Peridot property-sheet restage (menus, check boxes, Bold/Italic list) was rejected: a UI replica, not a picture; the mechanism would be invisible behind the chrome. A Garnet/Amulet widget-library replica (scrollbars, pull-down menus as the subject) was rejected: it restages the toolkit's demo inventory instead of turning one mechanism into art. A "programming by demonstration" tutorial or tool (draw a widget, get the code) was rejected: a tool, not a piece; it would be evaluated as software, not experienced as art. A dashboard or chart of constraint evaluations or inference confidence scores was rejected: a chart piece; the numbers would be the picture and there would be no picture. A biography or narrative piece (Myers's career, CMU, the gem-named systems as a timeline) was rejected: a biography, not a mechanism; nothing in it would compute. Any candidate whose primary interaction is click-to-reload was rejected: a forbidden pattern, and no prompt uses it. Any candidate using ?seed= as a clock or scene index was rejected: a forbidden repurposing, and no prompt varies by seed-as-time.
